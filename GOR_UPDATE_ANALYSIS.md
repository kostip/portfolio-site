## 2. Краткое резюме изменений

- Заголовок, первый вводный абзац, порядок основных разделов, обе таблицы и все 14 иллюстраций не изменились.
- Обновлён второй вводный абзац и добавлен новый абзац о рабочих сессиях с PM и геодезистом-экспертом.
- Первый пункт «Задачи бизнеса» полностью заменён: вместо прямого «Заменить QGIS» теперь объясняется, почему QGIS является избыточной альтернативой и какую логику нужно сохранить в GOR.
- Впервые появился блок h3 «Критерии успеха для MVP».
- Перед таблицами «Системные роли» и «Job Stories» появились поясняющие абзацы.
- Расширены объяснения в «Прототипах», «Интерактивной карте», «Режиме редактирования», «Экспорте», «Адаптивах» и «Мануале».
- В «Итогах» уточнён последний пункт и впервые добавлен отдельный абзац «Главный вывод».
- Целые существовавшие разделы не удалены и не переставлены. Добавленные блоки встроены в прежний порядок.
- Изображения старого экспорта, обновлённого экспорта и сайта побайтно идентичны. Ничего добавлять, заменять или удалять в `public/images/gor` не требуется.
- HTML подтверждает две двухколоночные композиции и две таблицы. Markdown теряет колонки, серые выделения, подчёркивания и часть принудительных переносов строк.
- Текущий `gor.md` в основном воспроизводит старый экспорт. Его структурные HTML-обёртки уже подходят для обновления, но перечисленные текстовые фрагменты устарели.
- Frontmatter менять не требуется: его заголовок и описание соответствуют обновлённому источнику, а роль, срок, команда и продукт не опровергаются новым текстом.

### Что Markdown упрощает или передаёт некорректно

1. Теряет обе `column-list` и их пропорции.
2. В заголовке Job Stories переносы внутри ячеек (`Когда` / `(обстоятельство)` и т. п.) представлены многострочным Markdown, который менее надёжен, чем текущие `<br>` в `<th>`.
3. Первый новый пункт «Задачи бизнеса» в Markdown продолжен следующей неотступленной строкой. HTML подтверждает, что это одна `<li>` с переносом `<br>`, а не отдельный абзац. При будущем переносе нужно оставить обе фразы внутри одного `<li>`.
4. Notion HTML хранит три серых выделения `<mark class="highlight-gray">`: подзаголовки разделов «Функционал сервиса», «Сценарий работы» и «Интерфейс карты». Markdown оставляет только текст. Текущий сайт тоже показывает их обычными абзацами. Решение о восстановлении визуального серого highlight нельзя принимать молча: отдельного существующего класса проекта для Notion-highlight не найдено. Без изменения CSS безопасно сохранить текущий обычный абзац.
5. HTML хранит подчёркивание через `border-bottom` у `200+ прототипов`, `426 макетов` и `127 страничный мануал` в четвёртом пункте итогов. Markdown и текущий `gor.md` это оформление теряют. Существующего специализированного класса для такого подчёркивания нет. На следующем этапе нужно отдельно решить: оставить обычный текст либо использовать семантическое `<u>`/локальную разметку без добавления глобального класса.
6. HTML хранит принудительные `<br>` внутри первого бизнес-пункта, первого абзаца мануала и жирных вводных частей четырёх итоговых пунктов. Markdown частично превращает их в обычные переносы. Текущий ручной HTML уже корректно сохраняет перенос в мануале; в итогах переносы можно оставить в структуре списка, как сейчас.
7. Notion HTML создаёт отдельный `<ul>` для каждого bullet-блока. Markdown визуально объединяет соседние пункты. На сайте правильнее сохранить один семантический список для каждого логического набора, как сделано сейчас.
8. HTML оборачивает каждую иллюстрацию в `<figure><a><img></a></figure>` и хранит экспортную ширину (обычно 864 px, для адаптивов 816 px, для мануала около 332 px). Подписей `<figcaption>` нет. На сайте не нужно переносить ссылку на исходный экспортный файл или inline-width.

### Существующие классы, которые следует использовать

Новых классов для переноса обновлённого текста не требуется. `.wide` не нужно вручную добавлять ко всем иллюстрациям: существующий селектор `.article-content > p:has(> img)` уже расширяет их.

20. После будущего изменения выполнить текстовый diff с `-UPD` с учётом намеренных структурных преобразований, проверить существование путей и только на том этапе запустить штатную проверку проекта. На текущем аналитическом этапе никакие сборки не нужны.

## 11. Список файлов, которые потребуется изменить на следующем этапе

Обязательно потребуется изменить только:

- `src/content/projects/gor.md` — обновить перечисленные текстовые фрагменты, сохранив существующий frontmatter и структурные HTML-обёртки.

Не потребуется изменять:

- `public/images/gor/*` — все файлы уже совпадают с обновлённым экспортом;
